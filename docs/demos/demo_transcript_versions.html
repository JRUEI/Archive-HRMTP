逐字稿版本差異

整理 HRMTP（本專案）逐字稿從 09-04 到 09-28 的幾個版本：各版怎麼做、差在哪、哪一版的問題最可能也出現在另一個專案。數字都是從 git 歷史逐版算出來的。

另一個專案給你的說法，大致正確

「09-05 那版是把已經翻好的中文逐列切句，09-28 起改成照 episode-workflow.md 由 LLM 直接逐句看字幕翻譯」：兩段都對。

「沒有腳本」只對一半。翻譯確實沒有腳本，但規則都寫成文件，最後還要用 validate-content.mjs --strict 擋，這一步才是穩定品質的關鍵。只抄 workflow 文件、不設驗證，效果會差很多。

為什麼 V2 的做法行不通

時間資訊只存在日文字幕裡。翻成中文之後，詞序已經重排（日文「第1回が配信された後」→ 中文「第 1 回播出之後」），中文一個字不一定對得到日文的哪個字。這時再拿中文切句，新的一列從哪一秒開始，只能用猜的或沿用上一列。

結論：要切句，就要在還看得到日文時間戳記時切，也就是邊看字幕邊翻、翻的時候決定一列到哪裡。已經翻好的中文，不要再拿來切列。

給另一個專案的調整清單

照 V3 的做法，最影響結果的是這幾項。前四項處理時間碼，後面處理一致性。

  1. 來源只認 VTT。舊的中文譯文最多當用語參考，不拿來切或改寫。
  2. 先處理滾動字幕。YouTube 自動字幕每個 cue 會重複上一行，要先去重，不然會翻出重複的列。
  3. 時間碼＝該列第一個字在字幕裡的時間。用 VTT 裡 <00:01:02.079> 這種逐字時間，不用 cue 的開始時間；格式統一 mm:ss。
  4. 相鄰兩列不同秒。同一秒開始的兩句併成一列；換人時後一列往後挪一秒。這條要讓驗證腳本擋，因為這是 V2 那種錯最直接的指標。
  5. 照句子切列，一列一個說話者，不超過 60 字。不要照字幕換行切（V1），也不要整段塞一列（V0）。
  6. 聲音標記有對照表。[笑い]→[笑聲] 等，[音楽] 不寫；只放在該列文字裡，不單獨成列。
  7. 人名先查詞表，再跑 dry-run。常客書籤名寫進 GLOSSARY；聽不出來就寫「……」，不要猜。
  8. 不加譯註、不補充、不摘要。口頭禪可以省略。
  9. 寫一支驗證腳本，警告也要清到零。至少檢查：時間碼遞增且不重複、說話者在名單內、單列字數、清單外的聲音標記、純標記列、整列重複。
  10. 規則改了就整批重做。V2.5 一個名字修一次，一直修不完；V3 全部重譯一次，各回才真的一致。

另一個專案的計畫：用 HRMTP 的時間碼比對

可以拿來抽查，但不要當標準答案。HRMTP 的時間碼同樣是 LLM 讀 VTT 決定的，不是程式算出來的。真正的標準是 VTT 的逐字時間戳記：拿另一個專案的某一列，找它第一個日文字在 VTT 的 <時間>，比 HRMTP 準。
