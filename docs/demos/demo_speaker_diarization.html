先講結論
  • 現在的標籤是 LLM 翻譯時順便從文意猜的。字幕檔沒有任何說話者資訊（12 個 VTT 裡 >> 換人記號 0 個），所以標籤從來沒有被聲音驗證過。
  • 拿文字線索回頭檢查，6 回 4,699 列裡有 215 列帶強線索（自我介紹、叫對方名字），跟標籤衝突的掃出 7 列，逐列讀過全是掃描規則誤報。也就是說，文字裡能用的線索當初都用上了，你聽到的錯誤，文字本身看不出來。
  • 可能的機制（推論）：沒有線索的長段落只能靠「一來一往」排，一旦有一句切錯或附和被併錯，後面整串就跟著錯位，到下一個線索才對回來，所以會出現整段對調。ep10 有 6 段超過 90 秒沒有任何線索，共 300 列（35%）。
  • 建議：不要用文字規則自動改標，它在 ep04、ep10 各提議改 1 列，2 列都是改錯。文字能做的是標出「沒把握」的段落，預先放進說話者標記工具的「待查」，你只要聽那些地方。真的要自動改，得用聲音（主持人聲紋比對，見最後一節）。

現在的流程

1. 抓字幕yt-dlp 抓 YouTube 日文自動字幕（content/epNN.ja.vtt）。只有文字和時間，沒有說話者。
2. 清洗去掉滾動字幕的重複行；舊腳本 scripts/legacy/fetch_and_process.js 輸出時說話者一律寫 [?]。
3. LLM 翻譯＋標說話者一段一段讀日文，同時切句、翻譯、決定說話者。依據只有文意：自我介紹、怎麼稱呼對方、問答順序、誰在唸信。
4. 人工修SpeakerMarks.tsx：邊聽邊按 [ ] S ?，套用後寫回 Markdown（只在 npm run dev）。

複驗：文字線索掃描（6 個來賓回）

腳本 scripts/speaker-cues.mjs。線索分兩類：有方向的（這列應該是誰）與相鄰的（這兩列不像同一個人）。

  • 強線索：「我是聲優福嶋晴菜」「福嶋晴菜的『はるまとぺーじ』」；「」外叫主持人（福ちゃん、福嶋さん）→ 說話的是來賓；叫來賓（さとはる、佐藤さん、侑里ちゃん、ねもちゃん…）→ 說話的是主持人。
  • 弱線索：唸信的框架句（書籤名「…」寄來的、信上這麼寫）；ep10 另加一張事實表（法學部、豐橋、三河腔屬於佐藤；荷官、矢神うしお屬於福嶋），列裡有「我」就是本人。
  • 相鄰疑點：同一人前一列提問、下一列回答；同一人自己附和自己；同一人收到稱讚後自己道謝；同一人覆誦自己的尾巴。

衝突與疑點逐列讀過的結果

  • 名字的誤報：ep10 23:53「已經越來越接近さとはる大師了喔」是佐藤在講自己，日文「里春マスターにどんどん近づいてますね」；ep04 15:12「妳有時候叫我福ちゃん」是福嶋轉述；ep12 35:50 同一列裡兩個名字都有；ep02 01:04 是來賓自我介紹。四列標籤都是對的，規則會改錯。
  • 唸信的人：ep10 15:50 起那封信是佐藤唸的，日文「じゃあ次のしおり読ませていただきますね」，標籤對。「誰唸信就是主持人」不成立。
  • 相鄰疑點：ep10 18:39「對對」是佐藤自己接著說（日文「〜じゃん。そう、そう。だから…」）；34:49 兩句都是福嶋對出題的聽眾吐槽；22:29「うん。そうね。うん。うん。」可能是福嶋附和，也可能是佐藤自己收尾，兩邊都通。6 回共 6 個疑點，0 個能從文字確定是錯。

錯誤型態（哪些是查到的、哪些是推論）

文字查得到的 已驗證
  • VTT 沒有說話者、沒有換人記號；字幕片段是滾動顯示的切法，常常一句切在中間（「…お / 2 / 人は」）。
  • 一個字幕片段裡常有兩個人：16:25「…とのことです。そう、あの万能カードだと思ってます。」、28:42「…ぐらい。うん。あ、分かる。バイト探す時…」、29:38「声優になれてよかった。うん。うちら良かったね。」換人點只能靠文意切。
  • ep10 有 29% 的列是 6 字以內的附和（嗯、對、真的嗎），誰說都通，只能照「一來一往」排。
  • 現有標籤跟所有文字線索一致（上表），所以文字側沒有東西可以再修。
推論、需要聽才能確認 未驗證
  • 整串對調＝相位錯位：無線索段裡某一處把兩句併成一人（或一人拆成兩人），後面的交替整個錯開一格，直到下一個名字或自我介紹才對回來。示範段 29:14–29:27 就是兩種相位都通的例子。
  • 單句錯：多半是插話與附和（「沒錯」「再見了」）被歸到旁邊那個人，或一列裡其實有兩個人。示範段 28:12 屬於這種。
  • 錯誤會集中在無線索的長段：ep10 的 06:00 前後、10:25–12:17、13:57–15:50、28:30–30:57、34:08–41:02（謎題單元，兩人都在唸題）。

優化方案

A. 文字側：不改標籤，改成「標出沒把握的地方」 已實作、零成本

  1. 跑 node scripts/speaker-cues.mjs 10：名字、自我介紹、事實表當錨點，算出每段離最近錨點多遠。
  2. 超過 90 秒沒有錨點的段落，整段預放一個「待查」；相鄰疑點那幾列也放。ep10 是 6 段（約 15.5 分鐘）＋ 3 列，不用整集 47 分鐘從頭聽。
  3. 這些標記可以直接寫成 SpeakerMarks.tsx 存在 localStorage 的格式（harumatope_speaker_marks_ep10，每筆 {type:'check', i, t}），打開工具就看到。這一步還沒接，要的話是幾行的事。
  4. 第二輪判讀（就是右欄）：LLM 對照日文字幕，只在「一句話被切成兩列」「回應詞開頭」這種結構證據夠時才改，其他寫理由標待查。示範段改 1 列、待查 14 列。

修得到：把要聽的範圍從整集縮到三分之一左右；一列裡同時有兩個人的地方會被標出來。
修不到：文字兩邊都通的地方（整串對調大多是這種），它只能說「這裡可能錯」，不能說「這裡是誰」。

B. 聲音側：主持人聲紋比對 只評估，沒有下載或安裝

每回固定兩個人，而且主持人有 6 回單人回（第 1、3、5、7、9、11 回），可以拿來當「福嶋的聲音長什麼樣」的範本。這比一般的說話者分離（不知道有幾個人、誰是誰）簡單很多：

  1. 從單人回取主持人聲紋（說話者嵌入向量的平均）。
  2. 來賓回每一列，用時間碼（本列到下一列）切出那段聲音，算跟主持人聲紋的相似度；來賓聲紋用文字錨點確定是來賓的那幾列（例如自我介紹）來取。
  3. 差距大的直接定案；差距小的（附和、重疊、笑聲）標待查，交給標記工具。
做法要準備的大概成本弱點
聲紋比對（SpeechBrain ECAPA、WeSpeaker 等嵌入模型）Python、PyTorch、模型檔（幾十 MB）、各回音訊一回幾分鐘（CPU 可跑）1 秒以下的附和、兩人同時說話
pyannote 說話者分離同上，加 Hugging Face 帳號與同意模型條款CPU 上可能接近片長，GPU 快很多同上；還要再對應「哪一群是福嶋」
whisperX（重新語音辨識＋對齊＋分離）同上，模型較大最重會產生新的日文稿，跟現有 VTT 時間碼要重新對

共同限制：逐字稿時間碼只到整秒、沒有結束時間；一列若混了兩個人，聲音側只能說「這列有兩個人」，要拆列還是得人工。音訊要從 YouTube 下載，下載與否由你決定，處理結果也只拿來改標籤、不另外散布。

跟手動標記工具怎麼搭

1. LLM 初稿跟現在一樣。
2. 線索掃描speaker-cues.mjs 找出無錨長段與疑點列。
3.（選配）聲紋比對有把握的直接改，沒把握的留著。
4. 預放「待查」寫進標記工具的 localStorage。
5. 人聽待查段用 [ ] S 標，套用、寫回。

建議

  1. 文字自動改標不要上線，它沒有東西可以修，還會改錯。
  2. 先用 A：把 ep10 的 6 段無錨長段當成聆聽清單，用現有工具修。之後新的一回照樣先跑掃描。
  3. 如果修完發現錯誤真的集中在無錨長段，再考慮 B 的聲紋比對；它是唯一能「自動」知道誰在說話的方法，代價是要裝 Python 環境、下載音訊。

怎麼開這頁

直接雙擊（file://）時 YouTube 會回錯誤 153，播放器出不來，字幕欄還是能看。要邊聽邊對，在專案根目錄跑：

npx --yes http-server docs/demos -p 8765 -c-1

再開 http://127.0.0.1:8765/demo_speaker_diarization.html。不要用 3000 埠，那是開發站。
